## 1. 交付顺序

默认按 **WP01 → WP02 → WP03 → WP04 → REL** 推进。阶段是业务验收边界，单元是日常开发和验证边界。每个单元包含使结果可用的数据库、接口、后端和后台改动。以表中的前置依赖为准。同一阶段内依赖已满足的单元可独立评审，单人实施默认按表序推进。

| 阶段 | 开发范围 | 阶段通过条件 |
| --- | --- | --- |
| [WP01 会话、知识问答与人工接管](specs/WP01_CONVERSATION_HANDOFF.md) | 本机环境、运营登录、事件接入、意图、两步 RAG、回复和轻量接管 | 测试消息从入口走到有依据的答复或人工待办，后台能核对处理与发送结果 |
| [WP02 身份、业务查询与导购](specs/WP02_COMMERCE_QUERY.md) | 核验、私密入口、订单物流、商品库存、活动权益和导购 | 公开与个人查询权限分开。并发查询、数据缺失和归属不符可复现 |
| [WP03 会员画像、互动与群复盘](specs/WP03_MEMBER_ACTIVITY_INSIGHTS.md) | 记忆、筛选、活动参与、知识编辑与群分析 | 运营可管理资料和活动、纠正画像、追查反馈依据。新结果反映更正后的知识与记忆 |
| [WP04 持续运营与任务恢复](specs/WP04_OPERATIONS_DELIVERY.md) | 计划、排期、规格订阅、事件模板、人工跟进、发送核实和恢复 | 触达按授权和有效状态执行，取消、历史事件、并发领取及发送不明不会导致误发 |
| REL 整体验收与交付 | 端到端回归、运营演练、可复现的本机运行和交付说明 | 12 项业务验收有证据，核心 Agent 有 DeepSeek 实测记录。渠道替身和真实联调分别标注 |

## 5. 单元如何进入实施、如何验收

1. **进入实施前**。核对前置结果、SPEC 和本次接口。WP01 使用 [10 项已定义的 OpenAPI 契约](openapi.wp01.json)。WP02–WP04 按具体单元补请求、响应、错误示例和授权。涉及新表、迁移、隐私或破坏性变更时，提交单元级细节供评审。首个单元已有单独 SPEC。
2. **验收分层**。单元验证业务、异常和必要的后台操作。阶段末验证从触发到后台结果的完整链路。全系统运行 A01–A12，以及数据库迁移、权限、并发、失败恢复和可复现运行检查。
3. **证据分开记录**。业务规则和接口用固定样例及测试 PostgreSQL 验证。模型替身验证编排与错误路径，真实 DeepSeek 验证语义和空输出等行为。运营后台人工走查，记录谁验证、使用的数据、结果和已知限制。
4. **外部依赖与完成定义**。本机版本完成要求所列业务范围通过集成和运营验收，DeepSeek 有实测，渠道缺失时有替身及业务降级证据。真实微信、商家及邮件联调分别记录能力、授权和结果。只有对应实际链路验证后才标为已接入。GitHub 发布和部署状态各自记录。
5. **计划变更**。实现过程中发现影响业务行为、API 兼容、数据归属或触达授权的变化，先更新对应基线和契约。状态使用待评审、实施中、已实现、已验证和已验收。未执行的验证保留未执行状态。
